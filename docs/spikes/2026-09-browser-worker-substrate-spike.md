# Spike S3: browser worker substrate (outside the agent VM)

> **Date:** 2026-09-14 · **Epic:** Agent Accounts & Credential Broker (`j471yhv7p3abea7mlxrchdu1`) · **Gate:** L0 → feeds L5a (G6a) · **Decision served:** D-19 (answered: worker outside the agent VM; this spike picks the concrete substrate) · **Liability:** Λ7 (browser profile / cookies reachable from the agent runtime)
> **Method:** document only. Every claim is marked **[repo]** (read from this checkout, with `file:line`), **[vendor]** (quoted from the vendor's own page on 2026-09-14), **[3P]** (third-party report only) or **UNVERIFIED** (nothing primary found). Nothing was provisioned; no paid service was touched.
> **Constraint carried over from Codex (review `km6yrydf0sc08g6ikoikno7f` §"Phase 5"):** typed navigate/click/type/read only; no raw CDP, JS eval, storage/cookie APIs, extensions, downloads; profile and CDP endpoint unreachable from sandbox processes; login is *exclusive human-control mode* with agent control **and observation** revoked; capture only approved session state; a cookie jar is not a universal session.

## TL;DR and the D-19 recommendation

**Recommendation for D-19:** *a separate Sprite per browser session* (Option 1) — Chromium driven by a worker process inside its own Firecracker VM over a debugging **pipe** (no CDP port exists), reached from PageSpace only through the existing preview relay under a new `browser` holder kind, network-pinned to the account's allowed origins by a transport-origin (TLS-or-plaintext + host + port) egress allowlist below the browser with the Sprite DNS policy as a host-level backstop, destroyed after every session, with captured session state living only in Infisical. **Browserbase without 1Password** (Option 2, minus its persisted contexts) is the costed fallback if G6a's first probe — *Chromium boots inside a Sprite* — fails. **A `browser` service in the tenant compose** running `steel-browser` behind an egress proxy (Option 3) is the onprem path, not costed.

Why Option 1 wins (scores in §7): it is the only option where **no vendor holds post-MFA session state at rest** (custody rule, Control Board §"One custody rule"), the observation cut is a state machine we own end to end, the live pane reuses the relay we already run in production, and the marginal cost is a Sprite-hour, not a second vendor contract. Its one open risk is empirical, not architectural: Chromium in Firecracker is reported both ways by third parties (§3.1) and must be the first probe of G6a.

What Browserbase + 1Password *actually* offers today (§4.3) does not fit the epic: the Agentic Autofill approval flow is Early Access **inside Browserbase Director only**, with no developer API; the developer-facing 1Password path resolves plaintext in the caller and passes it to an LLM instruction, which violates invariant 1. Persisted Browserbase "contexts" are encrypted, reference-by-id, non-exportable stores of cookies/localStorage/IndexedDB — a second credential plane we cannot audit. If Browserbase is used at all, contexts stay off and session state is captured through our own executor into Infisical.

## 1. What the substrate must do (requirements, Given/should)

These are the observable behaviours G6a/G6b/G6c will test. They are derived from the epic's invariants, Codex's Phase-5 rewrite and the S3 brief; each is stated so a table-driven test over a pure function, or a probe against a real worker, can decide it.

**Isolation (Λ7)**
- R1. Given any process in the agent sandbox (root, full egress), should be unable to open a TCP connection to the browser's CDP endpoint, read its profile directory, or read its cookie store — and the doc must name the *mechanism* per substrate, not the intent.
- R2. Given the browser worker's control channel, should accept commands only from the server-side tool executor (web app), never from the sandbox; a sandbox-originated request to the worker's URL should fail before authentication is even attempted.
- R3. Given a browser session ends (normally or by reclaim), should leave no profile, cookie store or checkpoint containing session state on the substrate; the only durable copy is the approved capture in the credential plane.

**Typed control (Codex §Phase 5)**
- R4. Given the agent, should be able to invoke only `browser_navigate`, `browser_click`, `browser_type`, `browser_read` (text / a11y snapshot / screenshot) and `browser_wait`; raw CDP, `evaluate`, cookie/storage APIs, extension install, downloads and file-system access should not exist as tool surfaces.
- R5. Given a typed action, should be refused unless the worker is in `agent-control` state **and** the target frame's origin is in the account's allowed origins at the moment of use (frame origin checked atomically with the action, not at navigation time).

**Live view and human-control mode**
- R6. Given a user with `use` permission on the account, should be able to open a live pane and see the browser's pixels and interact with it, authenticated by the same grant-cookie mechanism the dev preview uses; any other drive member should get 404.
- R7. Given the human enters human-control mode, should observe: every queued agent action drained and refused, the agent-facing screencast / snapshot / read streams closed, and an auditable counter of agent-visible events that stays at **0** until the human exits the mode.
- R8. Given human-control mode, should show the browser-verified top-level and frame destinations in **trusted PageSpace chrome** (app origin, outside the iframe), so a page cannot forge the address it is impersonating.
- R9. Given human-control mode ends, should destroy the login context and hydrate a *fresh* agent context from the approved capture only; the agent never resumes inside the context the human typed into.

**Session capture (Λ8)**
- R10. Given a capture, should include only state for the account's allowed origins (plus explicitly approved auxiliary origins), in a declared format (§5), and be written to the store as kind `session` with the format tag; whole profiles are never stored.
- R11. Given an account whose session depends on device-bound or unsupported state (§5.3), should be marked "re-login by human" at capture time rather than silently storing a capture that will not hydrate.

**Network confinement**
- R12. Given the browser worker, should be confined to the account's allowed origins plus approved auxiliary origins, with the sandbox internal-surface deny list (`egress.ts:69-78`) and private-IP ranges always blocked, enforced **below** the browser at **transport-origin granularity (secure-or-plaintext transport + host + port)** for every browser-initiated request — navigations, subresources, `fetch`/XHR, form submissions and WebSockets — by a request-interception or egress-proxy allowlist keyed on origin, with DNS policy as a hostname-level backstop only; never by DNS alone and not only in `navigate()`. (*Amended 2026-09-15*: the first draft allowed "DNS policy or egress proxy"; DNS cannot express scheme or port. *Amended 2026-09-16, PR #2633 round 4*: a non-intercepting proxy sees `https:` and `wss:` to the same host:port as the same `CONNECT host:443`, so `https:`+`wss:` form **one policy unit** and `http:`+`ws:` another; an allowed origin `https://example.com` therefore also admits `wss://example.com`. Splitting them needs TLS interception, which is out of scope for v1, see §3.5.)
- R13. Given a top-level navigation or redirect to an origin outside the set, should be blocked at the network layer and reported as a typed refusal; a subresource fetch outside the set should be refused at the worker egress proxy (transport origin: TLS-or-plaintext + host + port, §3.5) and logged.

**Cost and lifecycle**
- R14. Given a browser session, should be billed through `sandbox-billing.ts` as a machine with the browser's *actual* CPU/RAM shape, not the default `{1 vCPU, 0.25 GB}` (`credit-pricing.ts:336-337`).
- R15. Given an idle browser session past the session's grant lifetime, should be destroyed (not hibernated) so no session state lingers on disk.

## 3. Option 1 — a separate Sprite per browser session

### 3.1 What runs where
A Sprite is created per *browser session* (one account, one run), named from a new keyspace `browser-sprite:v1` via the existing `spriteNameFor` / `checkSpriteUrlLabelFits` (`sprites.ts:1231-1245`; labels must stay ≤ 63 chars, see memory on Sprite URL labels). Inside it: a Node worker (the only CDP client) launches Chromium with `--remote-debugging-pipe` and a per-context `--user-data-dir` under `/tmp`, listens on 8080, and holds the `HumanControlState` reducer. The worker is the *adapter*; every decision it acts on (`decideBrowserAction`, `reduceHumanControl`, `restrictFrameOrigin`, `selectCaptureState`) is a pure function in `packages/lib` under Control Board §7.

**Chromium-in-Firecracker is the unverified premise.** One report (2026-01) says Chrome's zygote crashes because Firecracker lacks kernel capabilities Chrome expects even with `--no-sandbox --disable-gpu`, and falls back to Lightpanda **[3P]**; a later report says Playwright's Chromium failed only because of default-deny egress during install and ran once egress was opened **[3P]**. The Sprite kernel is `6.12.105-fly` x86_64 with `node`/`bun` present (2026-08 spike §1 **[repo]**). No vendor statement exists → **G6a probe #1: boot headless Chromium (Playwright's build) in a 2 vCPU / 2 GB Sprite, open a page, take a screencast frame.** Lightpanda is *not* an acceptable fallback for login flows (partial JS/DOM fidelity); the fallback is Option 2.

### 3.2 Isolation: can a sandbox process reach the profile, CDP or cookie store? — No, by five mechanisms

| Reach `https://<browser-sprite>.sprites.app` | URL is `auth: 'sprite'`; without the org token the edge answers a **302 to SSO**, not the page (2026-08 spike §2 **[repo]**). Residual: anyone holding `SPRITES_API_TOKEN` owns every Sprite, browser Sprites included. That is a web-process compromise, already the accepted boundary for the agent sandbox; it does **not** widen with Option 1. Sprite checkpoints are disk-only and would snapshot a live profile — R3 therefore forbids checkpoints on browser Sprites (`checkpoint-policy.ts` must exclude the `browser` holder).

### 3.3 Live view pane and the observation cut
Path (reuse, with one new holder kind):
1. Pane opens `GET /api/drives/<driveId>/…/browser-sessions/<id>/preview/open` (session auth, `isAllowedPreviewOpen` Sec-Fetch checks, then a new `authorizeBrowserHolder` — **owner-with-`use`** on the account, not `isPrincipalDriveMember`; the env rule "any accepted member may VIEW" at `preview-access.ts:141` is wrong for a login pane and must not be inherited).
2. Grant → 302 → `https://bw-<id>.preview.<apex>/__pagespace/auth?grant=…` → `__Host-ps_preview` (10 min, `Partitioned`, HMAC over `{k:'browser',h,u,s,e}`) exactly as today (`preview-grant.ts:96-217`).
3. Viewer HTML + assets over the HTTP relay (allowlisted headers, `frame-ancestors <appOrigin>`, `no-store`) — the page is ours, served by the worker, so no upstream `Set-Cookie` sanitisation concerns.
4. Screencast + input over the WS tunnel: `apps/realtime` verifies cookie, a *present* `Origin` must equal the preview origin (a handshake with no `Origin` header is not refused, `preview-upgrade.ts:82`), then the server dials the Sprite and pipes raw frames (`preview-upgrade.ts:80-136`, `preview-ws-tunnel.ts:144-150`). The WS **cannot outlive the cookie** (`maxLifetimeMs = cookie.expiresAt - now`, `preview-upgrade.ts:136`) — a login longer than 10 min needs the postMessage re-grant already designed for the dev preview (memory: dev-preview dedicated origin). This is a feature: revocation of the account or the session ends the pane within the cookie window, and `isSessionUsable` cuts it per request before that.
5. Inside the worker, the human WS is tagged with `{userId, sessionId}` from the verified cookie payload. The relay sets that as `x-ps-preview-principal` on the **upstream** connection only, *after* `selectForwardableRequestHeaders` has filtered the client's headers: the verified claims are a separate argument to both relay paths (the HTTP relay and the WS tunnel in `preview-upgrade.ts`), and the header is set on the filtered map, never added to `FORWARDABLE_REQUEST_HEADERS` / `FORWARDABLE_UPGRADE_HEADERS` (`preview-proxy-policy.ts:175-183`) — those allowlists pass *client* headers through, so listing it there would let a preview caller choose its own principal. A client-supplied `x-ps-preview-principal` is dropped by the allowlist exactly as today. The worker accepts the header only on the org-token-authenticated upstream connection. That is **conditional**: the edge strips `Authorization`, so the worker itself cannot tell an edge-relayed connection from any other connection to port 8080. "No separate signing needed" holds only if G6a probe #2 shows that nothing except the Sprites edge can reach the worker port (no inter-Sprite reachability, and loopback callers inside the browser Sprite excluded). If that probe is inconclusive, the principal claim is signed like the control API (Ed25519, short-lived) and verified by the worker.

Observation cut (R7): `HumanControlState = 'agent-control' | 'draining' | 'human-control' | 'hydrating'`. `reduceHumanControl({state, event, now})` is pure; the worker: on `enter-human` → cancels the in-flight CDP command, refuses new `/control/*` calls with `{deny:'human-control'}`, unsubscribes `Page.screencastFrame` for the agent channel, stops serving `browser_read`, and starts a fresh screencast subscription bound to the human WS only. The count of agent-visible events during `human-control` is a worker counter exposed at `/control/audit` and is the G6a exit metric. Trusted chrome (R8): the worker forwards `Page.frameNavigated` (top-level and child frames, with `securityOrigin`) to the web app over the server channel; PageSpace renders them in its own DOM above the iframe. Clipboard, recordings and a11y snapshots do not exist as agent surfaces in this design, so there is nothing else to cut.

Exit of human mode (R9): `capture` → `Target.disposeBrowserContext` on the login context → new context hydrated from the approved capture → state `agent-control`. The login `--user-data-dir` is `rm -rf`'d; the Sprite is destroyed at session end (`stop` is already a delete, `sprites.ts` handle; never hibernate a browser Sprite).

### 3.4 Session capture (formats in §5)
Capture runs inside the worker as an *executor* against the login context: `Storage.getCookies` filtered by the pure `selectCaptureState({cookies, storage, allowedOrigins, auxiliaryOrigins, format})`, plus `localStorage`/IndexedDB via Playwright's `storageState({indexedDB: true})` when the account's format is `storage-state-v1` (Playwright ≥ 1.51 **[vendor]**). The result goes to the store adapter as kind `session` (frozen shape owner G1a; this spike adds no column) and is never returned to the model. Hydration is the inverse: `Storage.setCookies` / `addInitScript` into a fresh context.

### 3.5 Network confinement

*Amended 2026-09-15 (PR #2633 review).* The first draft let the Sprite DNS policy carry origin pinning. It cannot: a DNS rule for `example.com` admits **every scheme and every port** on that host, an origin is scheme + host + port, and **cookies are not port-scoped** — a session cookie captured for `https://example.com` is sent to `https://example.com:8443` alike, and a cookie without the `Secure` attribute is also sent to `http://example.com` (a `Secure` cookie is not sent over `http://`, but a login page's non-`Secure` cookies are, and the browser will happily *set* new ones there), so a second service on the same hostname or a plaintext listener is inside the pin. Top-level navigation checks do not cover subresources, `fetch`/XHR, form submissions or WebSockets. Confinement below the browser is therefore keyed on the **transport origin** (host + port + TLS-or-plaintext; `https:`/`wss:` are one unit because a non-intercepting proxy cannot tell them apart, per the round-4 note in R12), in three layers:

- **Egress proxy in the browser Sprite (the origin-level control):** Chromium starts with `--proxy-server=http://127.0.0.1:<port>` pointing at a proxy the worker runs (an *executor*; the decision is the pure `restrictRequestOrigin({scheme, host, port, allowedOrigins, auxiliaryOrigins})`). Every browser-initiated connection reaches it — `CONNECT host:port` for `https:`/`wss:`, absolute-URI requests for `http:`/`ws:` — so the proxy sees host, port and **transport** (TLS `CONNECT` vs plaintext absolute-URI) for navigations, subresources, `fetch`/XHR, forms and WebSocket handshakes alike, and refuses anything not in the origin set (`https://example.com` allows `CONNECT example.com:443` and nothing else on that host). **What it cannot see:** inside a `CONNECT` tunnel the scheme is encrypted, so `https://example.com` and `wss://example.com` are indistinguishable (both `CONNECT example.com:443`), and the interception layer below does not see WebSocket handshakes. The v1 policy unit is therefore the **transport origin**: `https:`/`wss:` on a host:port are one unit and `http:`/`ws:` another, and `restrictRequestOrigin` normalizes `wss→https` and `ws→http` before matching. That still enforces what cookies care about (port, and secure vs plaintext transport). An account that must allow HTTPS but refuse WebSockets on the same origin would need TLS termination at the worker proxy, with a worker-generated CA trusted only by that Chromium profile. That is out of scope for v1 and requires its own [D-n], since it puts plaintext of every request in the worker process. `Network.webSocketCreated` is logged for observability, not as a control. Chromium must not be able to bypass it: `--proxy-bypass-list="<-loopback>"` removes the implicit localhost bypass, and the DNS layer below denies resolution of every hostname **outside** the pinned set. A request that somehow skips the proxy is therefore bounded to the pinned hostnames, on any scheme or port. That residual is exactly the gap the proxy closes, so the proxy is the control and DNS is only the backstop. Design, not yet probed — G6a probe 3.
- **Request interception in the worker (defence in depth, observability):** `Fetch.enable({patterns:[{urlPattern:'*', requestStage:'Request'}]})` on every context, with the same `restrictRequestOrigin` deciding `continueRequest` vs `failRequest(BlockedByClient)`. This covers HTTP(S) requests at all stages (navigation, subresource, `fetch`, form) and is where blocked destinations are logged for the auxiliary-origin approval UI; it does **not** see WebSocket handshakes, which is why it is not the control.
- **Sprite DNS policy (hostname backstop):** `updateNetworkPolicy(buildBrowserNetworkPolicy({allowedOrigins, auxiliaryOrigins}))` — a sibling of `buildSpriteNetworkPolicy` (`egress.ts:175-212`) in `'allowlist'` mode: internal-surface denies first, one `allow` per pinned host, `DENY_ALL` last, `{include:'defaults'}` deliberately absent. Sprites additionally block private IPs and raw IPs not resolved from an allowed domain **[vendor]**. Precedence is by specificity, not order (`egress.ts:62-68`), which suits per-host pins. The policy file persists and reloads live (`egress-lockdown.ts:4-9`), so `shouldApplyPolicy` and the lockdown token apply unchanged. **What DNS policy gives:** no process in the Sprite — Chromium, the worker, or anything else — can resolve a hostname outside the set, which bounds the proxy's own upstream reach and closes the direct-resolution bypass. **What it does not give:** scheme, port, or path; any distinction between `https://example.com` and `http://example.com:8080`; and nothing at all for an origin the account legitimately pins whose hostname also serves something else.
- **In `navigate()`:** reuse `isAllowedFetchTarget` (`web-fetch-ssrf.ts:163-190`: HTTPS only, literal-encoding aware) and add the pure `restrictFrameOrigin`. Redirects are followed by the browser, so this check is user-facing hygiene (a clear error before the navigation starts), not the boundary; the boundary is the proxy above.
- **Egress IP:** browser Sprites must carry the dedicated `SANDBOX_EGRESS_IP_TAG` (`egress-ip.ts:33-53`); a browser logging into third-party sites from the shared production NAT IP is a stronger blocklisting hazard than a shell (§8, G2).
- **Auxiliary origins:** SSO IdPs and CDNs are real; the human approves observed frame destinations at capture time (R8 already shows them), stored on the account as `auxiliaryOrigins`. Not adding this makes half of enterprise logins impossible; adding it silently would be origin-pin erosion.

## 4. Option 2 — Browserbase (+ 1Password Agentic Autofill) for cloud

### 4.1 Isolation
Strong at the VM layer: "Each browser runs in a dedicated VM … in an isolated subnet with strict firewalls" **[vendor]**; SOC 2 Type II, BAA available, regions `us-west-2` (default) `us-east-1` `eu-central-1` `ap-southeast-1` **[vendor]**. A sandbox process cannot reach the profile (it is on Browserbase's VM). The CDP endpoint, however, is a public `wss://connect.browserbase.com/v1/sessions/<id>?apiKey=<key>` **[3P]** — *whoever holds the URL holds the browser*. The mechanism that keeps it from the sandbox is the same as Option 1's: the API key lives only in the server-side executor, never in `buildSandboxEnv`. Browserbase's own page does not document connect-URL access control or connection limits (UNVERIFIED), so we must assume a leaked URL is a leaked session.

### 4.2 Live view and observation cut
`sessions.debug(id)` returns `debuggerFullscreenUrl` / `debuggerUrl` (+ `wsUrl`), iframe-embeddable; read-only via `pointer-events: none`, read/write via `sandbox="allow-same-origin allow-scripts"`; a `browserbase-disconnected` postMessage on end **[vendor]**. **Auth on that URL, its expiry, mid-session revocation and whether the automation CDP connection is cut when a human takes control are all undocumented — UNVERIFIED.** So the pane would be Browserbase's origin inside our iframe (R8 still satisfied by our chrome, but frame URLs would have to come from our CDP client, i.e. we must *stay connected* to observe the address bar — contradicting the observation cut). Recording is **on by default** and would record the login (`recordSession: false` mandatory; Live View survives that) **[vendor]**. Observation cut therefore = our executor disconnects CDP entirely during human mode, and the trusted URL display is unavailable during exactly the phase that needs it. This is the decisive functional gap against R8.

### 4.3 1Password: what "human-approved, per-session, no standing access" really means
Two different things share the name **[vendor]**:
1. **SDK quickstart** (`@1password/sdk`, `OP_SERVICE_ACCOUNT_TOKEN`, `client.secrets.resolve("op://…")` → plaintext → `stagehand.act(\`Type in the username: ${username}\`)`): no human approval, plaintext in our process and in an LLM instruction. Violates invariant 1 outright.
2. **Secure Agentic Autofill**: per-fill approval from the user's 1Password desktop/mobile app; item sent encrypted over a Noise-framework channel to a headless 1Password extension in the remote browser, which injects "only the minimum required credential data"; "Raw credentials never enter the LLM context". The phrase "no standing access" does not appear; the equivalent is "Any request made for credentials must be approved by a human by default". **Availability: Early Access, inside Browserbase Director (no-code agent) only; pairing partner is validated as `director.ai`; no developer API or SDK is documented.** Business accounts need an admin policy switch.
Conclusion: (2) is the right *shape* (it is G6c's fill model, vault-side), but it is not callable from our executor today, and (1) is disqualified. Neither answers G6b (sessions), which is the epic's first browser deliverable.

### 4.4 Session state: export/import
Contexts persist "Cookies, localStorage, IndexedDB, Session Storage, Service Workers, Web Data, Browser preferences", are "uniquely encrypted at rest", and are used by id (`context: {id, persist: true}`) **[vendor]**. No export/import endpoint is documented (absence verified on the contexts and create-session pages; exhaustive-API absence UNVERIFIED). Under the custody rule a persisted context **is a credential plane we do not control** (post-MFA cookies at rest, no per-tenant identity, no audit-before-use). So contexts are **off**; capture happens through our CDP client into Infisical exactly as in §3.4, and hydration into a fresh Browserbase session via `connectOverCDP` + `storageState`. That works, but it means Option 2 buys only the VM and the pixels.

### 4.5 Network confinement
`browserSettings.allowedDomains` (domain-based, not full-URL — the same hostname-not-origin gap as §3.5, so scheme and port are not enforced by it) and proxy rules with `"type":"none"` exclusions **[vendor]** map to `allowedOrigins`/`auxiliaryOrigins`; origin-level enforcement would have to ride Browserbase's proxy rules or our own request interception. Their built-in proxies refuse banking, government, webmail and similar categories **[vendor]** — relevant if a user's target is one of them. Our `egress.ts` internal-surface deny list is irrelevant (their network), and `web-fetch-ssrf.ts` still guards `navigate()`.

## 5. Session capture formats ("a cookie jar is not a universal session")

Supported formats are declared on the account at capture time; the pure `classifySessionDependencies({cookies, storageKeys, observedApis})` picks one or refuses (R11).

| Format tag | Contents | Hydrates into | Covers |
|---|---|---|---|
| `cookie-jar-v1` | cookies for allowed + auxiliary origins (name, value, domain, path, expires, secure, httpOnly, sameSite) | `Storage.setCookies` | classic server-session sites |
| `storage-state-v1` | cookie-jar-v1 + `localStorage` + IndexedDB per origin (Playwright `storageState({indexedDB:true})`, ≥ 1.51 **[vendor]**) | `storageState` on a fresh context | SPA / OIDC-in-browser sites that keep tokens in web storage |
| *unsupported* → `human-relogin` | device-bound keys (WebAuthn/passkeys, Chrome Device Bound Session Credentials), service-worker state, client certificates, HTTP-cache-dependent sessions, OS keychain items | nothing; every run starts in human-control mode | evolving; Google accounts with DBSC are the first known case (UNVERIFIED which accounts today) |

Never stored: whole `user-data-dir`, HTTP cache, history, extension state, anything outside the origin set. Capture and hydration are executors; selection and filtering are pure and table-tested (lookalike origins, parent-domain cookies, `Partitioned` cookies, expired entries).

## 6. Option 3 — a browser service in the tenant compose (onprem path, not costed)

`infrastructure/docker-compose.tenant.yml` has an `internal` bridge network with `internal: true` (no egress) and a `traefik` external network; only `web` and `realtime` join both; services reach each other by compose name (`http://processor:3003`) **[repo]** `:298-303, :199, :285`. A `browser` service (`ghcr.io/steel-dev/steel-browser`, Apache 2.0 **[vendor]**; or plain Chromium + our worker image, which keeps one worker codebase across Options 1 and 3) is added on `internal` (for the relay from `realtime`/`web`) **and** `browser_proxy` (to reach its forward proxy; see below), `expose: 8080`, memory limit, `read_only` + `tmpfs` like `processor` (`:120-178`). Because `internal` has no egress, the proxy sits on a **two-network boundary**. `browser_proxy` (`internal: true`) is joined only by `browser` and a tiny allowlisting forward proxy (squid/tinyproxy, allowlist rewritten per session from `allowedOrigins`). `browser_egress` (not internal) is joined **only by the proxy**. The browser container is never on an egress-capable network, so the proxy is its sole route off-host. Joining `browser` to `browser_egress` would let traffic bypass the allowlist and violate R12; Chromium runs with `--proxy-server` and `--proxy-bypass-list=<-loopback>`. Isolation: separate container, no shared volume with `web`; CDP on a pipe inside the container; the sandbox in onprem (local substrate) has no route to `browser` because the sandbox is not on `internal`. Live view: the same relay code path with a `browser` holder whose upstream is `http://browser:8080` instead of a `.sprites.app` URL — `assertTrustedPreviewUpstream` (`preview-proxy-policy.ts:76-91`) needs a substrate-aware branch, which is the one relay change Option 3 forces. Not costed (D-21: onprem not a priority); Λ11 applies in full — the operator sees everything.

## 9. What this spike is NOT, and what it hands to G6a

Not product code, not a shape change: the account schema, grant shape and store interface stay G1a's (Control Board §1). It does not ask for a new [D-n]; the fallback in §7 would. It does not verify Chromium in a Sprite, inter-Sprite reachability, or Browserbase live-URL auth — those are the first probes of G6a, in order:
1. Chromium (Playwright build) boots and screencasts in a 2 vCPU / 2 GB Sprite; measure launch time and RSS. **Go/no-go for Option 1.**
2. From an agent Sprite: `curl https://<browser-sprite>.sprites.app` → expect 302 to SSO; `curl http://<browser-sprite-private-ip>:8080` → expect unreachable. Feed to `assessContainment`.
3. `updateNetworkPolicy` with a two-host allowlist **and** the worker egress proxy with a transport-origin allowlist (§3.5); `navigate()` to a third host → refused at the worker egress proxy (with `--proxy-server` Chromium does not resolve names locally, so expect `ERR_TUNNEL_CONNECTION_FAILED` for `https:`, or the proxy's typed refusal for `http:`), and separately a direct `getaddrinfo` of that host from a non-proxied process in the Sprite → DNS `REFUSED`; a page-initiated `fetch()`, `<img>`, form POST and `new WebSocket()` to an *allowed* host on a non-listed port or over `http:`/`ws:` → refused at the proxy (and `wss:` to the allowed host:443 recorded as **admitted**, confirming the transport-origin unit) (`ERR_TUNNEL_CONNECTION_FAILED` / `ERR_PROXY_CONNECTION_FAILED`), and `<-loopback>` confirmed to remove the proxy bypass.
4. Human-control blackout: agent event counter = 0 across a scripted 60 s human session (G6a exit metric).

**One line for D-19:** Option 1 — a per-session browser Sprite with the worker inside it, reached only through the preview relay under a `browser` holder, origin-pinned by transport origin (TLS-or-plaintext + host + port; `https:`/`wss:` one unit, R12) at a worker-run egress proxy with DNS policy as backstop, never checkpointed, destroyed after capture; Browserbase without contexts or 1Password is the fallback if Chromium will not boot in a Sprite; `steel-browser` in the tenant compose is the onprem path.

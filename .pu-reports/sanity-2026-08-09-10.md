## Finding 1 — HIGH · `agent_workspace_nodes` is an undecided table in the tenant export

`ci / Unit Tests` fails on `scripts/__tests__/tenant-export-columns.test.ts:250`:

```
AssertionError: agent_workspace_node_revs, agent_workspace_nodes reference a table the tenant
export carries, but nothing says whether they travel. Add them to TABLE_IMPORT_ORDER (plus a
spec in TENANT_EXPORT_COLUMNS and a query in tenant-export.ts / tenant-validate.ts), or to
TENANT_EXPORT_EXCLUDED_TABLES with a reason. A table nobody decided about is dropped from
every tenant migration and no test notices.
  expected [ 'agent_workspace_node_revs', 'agent_workspace_nodes' ] to deeply equal []
```

Still present at epic tip `656785640`: neither table appears in `TABLE_IMPORT_ORDER` nor in
`TENANT_EXPORT_EXCLUDED_TABLES`. `scripts/tenant-export.ts:283` states the gap in a comment
— *"`agent_workspace_nodes` is an undecided table"* — while querying that same table at line 291.

**Why this outranks everything else on the list.** Before this epic a thread's workspace was
`conversations."workspaceId"`, an ordinary carried column. Migration `0256` drops that column
and `agent_workspace_pane_columns` / `agent_workspace_panes` outright, with no down migration.
After `0256`, `agent_workspace_nodes` is the *only* record of both membership and layout. A
tenant export run against a migrated database therefore carries neither — every workspace
arrives at the destination empty and every thread arrives with no workspace, and by the
registry test's own words, *no test notices*. The pre-`0256` posture (membership in a carried
column) is what made this table's absence survivable; `0256` removes exactly that.

`apps/web/src/components/layout/left-sidebar/AgentsSidebar.tsx:610` documents that row
membership "comes from the LIVE tree… by the listing and never by the tree", so the seam is
between the realtime close event and the listing cache key the sidebar now reads — the epic
renamed and re-homed both sides of that pairing.

## Checks that came back CLEAN

**The re-parenting hazard — clean.** This was the one I most expected to find something in,
and there is nothing. Every named pattern was swept across `packages/lib/src`,
`apps/web/src`, `apps/realtime/src`, `packages/db/src`.

One grep hit, investigated and **cleared**:
`apps/web/src/lib/agent-workspaces/workspace-node-placement.ts:291` —
`const parentId = command.parentId ?? root?.id;`

This is not a failure-path re-parent. It defaults an **omitted** argument on the `arrange`
(reorder) command, whose `parentId` is optional by type and means "the root's own children" —
the top-level ordering `reorder_columns` meant. It is immediately followed by two refusals:
`no_root` when there is no root, and `unknown_parent` when the resolved id names no node. No
node's `parentId` is written on any error branch. Legitimate.

Every other match on `attach to root` / `reattach` / `reparent` is prose or a test asserting
the refusal, including `workspace-node-validate.test.ts:520` ("should reject an unresolvable
parentId rather than repairing it by re-parenting to the root"),
`workspace-node-rows.test.ts:390`, `workspace-node-write.test.ts:142` and
`workspace-node-commands.test.ts:890/901`. The four load-bearing decisions from the epic
page hold: no `rootId` in the in-memory model, composite self-FK on rows, membership and
location as different columns, and no fallback re-parenting anywhere.

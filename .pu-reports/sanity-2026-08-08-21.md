## 5 — the re-parenting hazard: **CLEAN**, and defended better than the plan asked for

This was the highest-severity item to check. I looked for `?? root`, `|| root`, "attach to
root", and any `parentId` assignment reachable from a `catch`, `else`, or not-found branch,
across every file the epic touches. **There is not one.** Reads of the form
`const parentId = node.parentId` are present and legitimate.

All four load-bearing decisions from the epic's hazard section are intact:

1. **No `rootId` on the in-memory model** — confirmed. `WorkspaceNode` has no `rootId`
   field; cross-workspace parenting is unspellable in the algebra.
2. **Composite self-FK** — confirmed in `0255_boring_leo.sql`:
   `FOREIGN KEY ("rootId","parentId") REFERENCES agent_workspace_nodes("rootId","id")`,
   on a `PRIMARY KEY("rootId","id")`. A cross-workspace parent is a database error.
3. **Membership and location are different columns** — `rootId` NOT NULL, `parentId`
   nullable, with `CHECK (nodeType <> 'root' OR parentId IS NULL)`.
4. **No fallback re-parenting** — the strongest of the four, and enforced at four layers:
   - `workspace-node-write.ts` carries an explicit module-level contract ("There is no
     `parentId` assignment anywhere in this file — not on a success path and certainly not
     on a failure one") and a `foreign_scope` refusal ordered **first, before the rev
     check**, so a cross-workspace payload is answered 400 and never 409-with-truth — which
     would invite the caller to resend it against a fresher rev. Tested by name:
     *"refuses BEFORE the rev check, so a cross-workspace payload is never invited to rebase."*
   - `nodesFromRows(rows, rootId)` takes the expected `rootId` as a required parameter and
     **throws** on the first foreign row rather than dropping it.
   - The store forces scope from the URL: `rowFromNode(node, workspaceId)` on every upsert,
     and `DELETE ... WHERE rootId = workspaceId AND id IN (...)` — the comment correctly
     notes ids are client-minted, so a bare `id IN (...)` would delete another workspace's rows.
   - The wire type goes **further than the plan specified**. The plan said the `put` route
     should reject a payload node whose `rootId` differs. The implementation makes `rootId`
     *optional on the wire and checked when present*, and stops it at the boundary — "This
     is where `rootId` stops. A node's workspace is decided by the URL."

   The three server-side placement entry points refuse rather than re-home:
   `findWorkspaceOfConversation` returns `null` and every caller early-returns; a chat
   target already bound anywhere is refused by `target_already_shown` in the algebra *and*
   by `UNIQUE (targetId) WHERE targetKind = 'chat'` in the table.

Named tests exist at each layer, including
`workspace-node-validate.test.ts:507` *"should reject an unresolvable parentId rather than
repairing it by re-parenting to the root"* and `workspace-node-rows.test.ts:372` *"should
surface a node whose parent does not resolve, and never re-parent it onto the root"*.

I found nothing to report here. Recording that explicitly so a future audit does not have to
re-derive it.

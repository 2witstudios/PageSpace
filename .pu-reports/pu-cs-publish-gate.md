## Gate order and outcomes

Order, before any copy:
1. The blocklist, in every mode including `off`.
2. A fresh verdict:
   - `clean` within the TTL → promote, no scan.
   - `flagged` from the classifier within the TTL → no rescan and no new case; held under enforce.
   - `error` never short-circuits: the next publish retries.
3. Read the original (bounded), sniff it, scan it with the timeout.

| Outcome | enforce | shadow |
|---|---|---|
| blocklisted | refused | refused |
| clean | record, promote | record, promote |
| hash_match | not promoted. PR 2 global takedown, category `csam`, as the system (block source `hash_match`): blocks, preserves, removes everywhere, including an existing public copy, opens its case, alerts. Verdict `flagged/hash_match`. | **same: not promoted, takedown runs** |
| classifier_flag | not promoted; review case opened or joined and verdict `flagged` (with the case ID) recorded **in one transaction**, under the case's row lock, so a dismissal and a late flag serialise: a flag never lands behind a closed case. Urgent alert when the case is new or had no flag before (a report's case). If the case can't be opened, verdict `error` instead, so the next publish rescans and retries. No block, no takedown | same records, case and alert; **promoted** |
| error / timeout / too large / unreadable | not promoted; verdict `error`; retried on republish | recorded; promoted |
| archive, executable, our encrypted envelope, **any bytes nothing recognises (whatever the declared type)**, an image or video Hive can't read (BMP, TIFF, HEIC, AVIF, ICO, JPEG XL, JPEG 2000, WebM/Matroska, AVI, Ogg video), text claiming to be a raster image | not promoted; verdict `unscanned` (cached for the TTL) | recorded; promoted |
| PDF (`%PDF-`); **a whole file** that reads as text (no NUL or stray control bytes; valid UTF-8, BOM'd UTF-16, or at 64 bytes or more a single-byte encoding such as Latin-1: text, CSS, JSON, SVG, …); recognised audio (ID3/MPEG, AAC, FLAC, WAV, AIFF, MIDI, AMR; Ogg only when the whole file is read and every stream in every link is an audio codec; an M4A-branded MP4 only when the whole file is read and every track handler is sound); recognised fonts (WOFF/WOFF2, and OTF/TTF with a plausible table count); a zip whose **first entry** is `[Content_Types].xml`, `_rels/.rels` or `mimetype` (OOXML/ODF/EPUB, by the bytes alone, not the declared type); legacy OLE Office | promoted unscanned; verdict `unscanned` (cached for the TTL, not re-read); audited | same |
| no vendor key | **nothing promoted** (fails closed), error logged once | promoted, warning logged once |
| `off` (default; always on-prem) | blocklist only, as today | — |

**The bytes decide, not the declared type.** The uploader controls `mimeType`, and a JPEG labelled `application/pdf` would otherwise skip the scan and still render in an `<img>`. The declared type only separates a document from an archive in the same container, and a claimed picture from text. Unrecognised bytes are opaque.

### Scan input: bytes, not a presigned URL

The gate reads the original from the private bucket and posts it to Hive as multipart `media`:

- **No capability URL leaves our infrastructure.** Nothing is left that the vendor, or its logs, could replay to fetch a private object.
- **We sniff the same bytes we send.** The declared type can't steer the scan.
- **The read is bounded.** A HEAD comes first. A file over `CONTENT_SCAN_MAX_BYTES` is never buffered: only its first 4 KB are read, to classify it. An image or video over the bound is a scan error, never a pass.
- **Bounded work per publish.** Assets are gated four at a time; the private read has a 30 s timeout; a type published unscanned is remembered for the TTL, so it is not re-read on every republish. A scanned file is still read twice (once for the scan, once by the copy), and the copy now runs even for an already-public file, since the gate goes first.
- **Encrypted objects stay unreadable.** If an original were an at-rest envelope (`PSE1`), a presigned URL would hand the vendor ciphertext. The gate sniffs the magic and treats the file as opaque, which enforce never promotes. Today the web upload path writes plaintext, and the processor's encrypting writer has no production callers (PR 1 report).

## Hive assumptions to confirm with the vendor

From Hive's public docs ("CSAM Detection - Combined API", reference and guide pages, read 2026-11-13). Each one is marked `ASSUMPTION` in `scanner-hive.ts`.

1. **Sync uploads.** `POST https://api.thehive.ai/api/v2/task/sync` accepts a multipart **`media`** upload. The docs show `media` only on `/task/async`, and only `url` on sync.
2. **Auth and project.** The auth header is `Authorization: Token <key>`, and the key is the CSAM project's own key.
3. **Success code.** Success is `status[0].status.code` = 200 (I also accept `"0"`), with the result at `status[0].response.output.{file, hashes}`.
4. **What counts as a match.** It is a `hashes[]` entry with a non-test `sources[].hashSet`. Any `matchTypes` value (`CSAM`, `SE`) counts, and is taken down as `csam`.
   - Is `SE` (sexual exploitation) right to treat as `csam` for a global takedown?
5. **Test lists.** `hashSet` values `test` and `test-se` are Thorn's test lists, ignored unless `HIVE_INCLUDE_TEST_MATCHES=true`.
   - A file-level `reasons: ["matched"]` with no source at all is treated as an error, not clean.
6. **Classifier output.** It is `file.classifierPrediction.csam_classifier.{csam, pornography, other}`.
   - We flag on `reasons` containing `csam` **or** `csam ≥ 0.9`. Confirm Hive's own threshold and what you recommend.
7. **No prediction means clean.** A **null** `classifierPrediction` with no match is mapped to **clean**, and the verdict row records `classifier: false`. The docs say it is null when the classifier fails, for example below 100×100 after de-letterboxing, and every video example has null. If the classifier does run on video, or a null means "couldn't check", this must become an error under enforce.
8. **Supported types.** jpg, png, gif, webp, mp4 and mov. Hashing needs ≥50×50. **Not published:** size limits, duration limits, rate limits, error body format, HTTP error codes, retention of submitted media, pricing.
9. **Matches and NCMEC.** Is a match against Thorn/NCMEC lists through this API reportable by us via NCMEC's CyberTipline? Is that what Arbiter covers?
10. **Testing method.** What test media does the vendor provide to exercise the hash-match path end to end in staging (assumption 5)?

## Known gaps

These are real ways around the gate, stated openly:

- **Inline `data:` images** in canvas HTML never pass through the asset pipeline.
- **Published apps** run customer code on their own domains and can serve anything.
- **External image URLs** in published pages aren't ours, but they appear on our domains.
- **PDFs** are published unscanned and can contain images. The same goes for office documents and SVG, which can embed rasters. A zip is treated as a document by its first entry alone, so a zip of images with a dummy `[Content_Types].xml` first is published: that is the same gap (a real docx can carry any images), and the cost to an attacker is one entry.
- **Large files** are classified on their first 4 KB. Over `CONTENT_SCAN_MAX_BYTES`, text is not trusted (held under enforce), and an image or video is a `too_large` error (held); a PDF or recognised audio/font/document over the bound is still published unscanned.
- **A PDF's or document's thumbnail** is published as an image, but is gated as its original (a PDF, so unscanned), as the brief requires.
- **Assets already public** before this PR are unchecked until something republishes them (the PR 5 backfill).
- **Cost.** Every publish of a file whose clean verdict has expired, or whose last scan errored, calls the vendor again. Flagged files are not rescanned within the TTL.
- **Image types Hive can't read** (BMP, TIFF, HEIC, AVIF, WebM, AVI) and files over the size bound are **held under enforce**. That will refuse some legitimate sites; shadow-mode counts will show how many.
- **The 404 page and canonical republish** (`renderNotFoundPageHtml`, `republishDriveCanonical`) run the gate, but their held assets aren't reported anywhere except the audit log.
- **Video with no classifier output anywhere is clean** (assumption 7). The hash pass ran; whether the classifier runs on video is for the vendor to confirm. If it doesn't, enforce relies on hash matching alone for video.
- **ICO favicons are held under enforce** (Hive can't read ICO). Use PNG favicons.
- **A hash-match takedown runs inside the publish request.** It is rare, but it makes that publish slow. A failed step leaves the case resumable from the console and the file not promoted.

## Decisions recorded

- **Shadow mode still refuses blocklisted hashes and still acts on hash matches**, per the brief: "a known-CSAM match is never shadow".
- **Flag alerts are urgent.** In shadow mode the file is live on the web.
- **A classifier flag stands while it is fresh or its case is under review.** A clean, failed or unscanned result from another publish of the same hash cannot overwrite it; the write reports that it kept the flag and enforce holds that publish too. Only a dismissal or a hash match replaces it; an expired flag whose case is closed is replaced by the next verdict.
- **Text is never cached as allowed or held.** Whether text may publish depends on each upload's declared type, so it is re-read each time. Other unscanned classes are decided by the bytes alone and stay cached.
- **A `mimetype` first entry counts only when it is a real ODF/EPUB marker** (stored, naming a document type). Any other zip is an archive. A zip with `[Content_Types].xml` first is still trusted as OOXML: proving more would mean inflating the archive, and a real document can embed images anyway (the known gap).
- **One review case per hash.** A flag on a hash that already has a reported case (from a user report or an earlier flag) joins it. The category becomes CSAM, a triage label, not a finding.
- **Dismissing a flagged case clears the hash** with a `clean` verdict (`admin_review`), written in the close's own transaction. Otherwise a false positive would be held forever under enforce. The close is refused (409) if the case's scan flag differs from the one the admin was shown (`expectedScanFlaggedAt`), as it already was for a changed report count, so a flag that joined after the admin looked is never dismissed unseen.
- **A CSAM case opening alerts as urgent** (`[URGENT] CSAM case:`): that is how a known-hash match from the gate arrives.
- **Gate logs carry an error's name and code only.** A query error's message carries the SQL parameters (the hash and scores).
- **`copyAssetToPublishBucket` is ungated.** It stays, because tests use it, with a doc comment saying production code must go through `promoteAsset`.
- **`heldAssets` includes copy failures as well as gate refusals.** The user sees the same neutral message, with no reason.
- **The OG image and favicon flows keep their existing 400** ("Selected image is unavailable or not accessible") when held. They don't return `heldAssets`.

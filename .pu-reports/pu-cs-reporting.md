## What exists now

### Data model (`packages/db/src/schema/content-safety.ts`)

- **`content_cases.status` gains `reported`**: opened by reports, waiting for staff. The column is `text`, so the
  status itself needs no migration.
- **One case under review per target**: partial unique index `content_cases_reported_target_key` on
  `(target_type, target_id) WHERE status = 'reported'`. Two reports that arrive at once land on one case.
- **`content_reports`** (new table, no FKs like its neighbours): `id`, `case_id`, `category`, `description`,
  `source` (`signed_in` | `anonymous`), `reporter_user_id`, `contact_email`, `created_at`. **No IP or user-agent
  column** (a schema test asserts it). The report count is the number of rows for the case.
- `ContentCaseSnapshot.review` records how staff closed a reported case (outcome, admin ID, note, time).
- Migration `packages/db/drizzle/0384_content_reports.sql`, generated by `bun run db:generate`. Same numbering
  quirk as PR 1: drizzle-kit named it `0353_complete_energizer` and overwrote `meta/0353_snapshot.json`; I
  restored that snapshot from git and renamed the new files to `0384_*` with the journal tag to match. SQL
  untouched. A second `db:generate` reports "No schema changes". Applied to the test database.
- Audit event types (`security-audit.ts`): `content.report.created`, `content.report.attached`,
  `content.report.resolved`.

### Lib (`packages/lib/src/content-safety/`)

- `reports.ts` (pure): categories (`csam`, `illegal_other`, `malware`, `copyright`, `harassment`, `other`), the
  signed-in and public request schemas, `classifyReportUrl` (published-host check), `caseCategoryAfterReport`
  (a report of illegal content categorises the case; CSAM always wins and is never downgraded),
  `CSAM_REPORT_GUIDANCE`, and the neutral refusal messages.
- `report-intake.ts`: `submitContentReport(submission, deps)` — every effect is a dependency. Resolves the target
  with `resolveTakedownTarget`, checks the reporter can see it, files it, audits it, alerts. There is no
  takedown, block or unpublish dependency at all.
- `report-store.ts`: `fileContentReport` (insert-or-join in one transaction, row lock so each report sees its
  own count), `listReportedCases` (CSAM first), `attachReports`, `closeReportedCase` (same row lock; refused with
  `ReportedCaseChangedError` → 409 if more reports arrived than the admin saw), `findPublishedSiteDrive` (the drive
  of a *visible* published site for a host: not held, not hidden by org policy).
- `alerts.ts`: `sendContentSafetyAlert` takes report alerts too (`report_opened`, `report_added`). The email
  has case ID, category, report count and the admin link only. A CSAM report's subject starts
  `[URGENT] CSAM report:` and is sent with `X-Priority: 1`, `Importance: high`, `Priority: urgent`. Each report
  has its own idempotency key (`content-case:<id>:report:<count>`).
- Rate limit `DISTRIBUTED_RATE_LIMITS.CONTENT_REPORT`: 10 per hour per IP.

## Decisions recorded

- **User targets are not visibility-checked**, because no central "can see this user" function exists and the
  legacy route never checked. Instead a report about a user ID that does not exist gets the same 201 as a real
  one and files nothing, so the route cannot test whether an ID exists. Self-reports are refused.
- **A file whose ID is its content hash files against the hash** (`content_hash` target), so reports about the
  same bytes through a file ID or a published asset URL share one case.
- **A reported case and a takedown case are separate.** Staff run the takedown from Take down (its own case, as
  in PR 2) and then mark the report actioned. Closing a report doesn't run anything, and running a takedown
  doesn't close the report automatically.
- **The reporter is never given the case ID.**
- **The URL a visitor typed is not stored**, as in PR 2's resolver: the case names the page or drive it resolved
  to. Staff see the page/drive ID, not the address.
- **Anonymous reports are audited without the reporter's IP or user agent** (`audit()`, not `auditRequest`), so
  nothing ties a visitor to a case. The IP is used only as the rate-limit key. Signed-in reports are audited as
  usual.
- **Admin vitest now uses the automatic JSX runtime** (`esbuild: { jsx: 'automatic' }`), needed for the first
  component test in that app.

## Open questions for counsel

1. **Retention of reporter text and contact emails.** `content_reports.description` and `contact_email` have no
   expiry. How long may we keep them, and must they go once a case is closed?
2. **Erasure.** A signed-in reporter's user ID, and a visitor's contact email, survive account erasure (no FKs,
   by design for evidence). Is that acceptable for the reporter's own data, or should erasure null them on
   closed cases?
3. **No IP for anonymous reporters, anywhere.** That protects reporters but means we can't trace a visitor who
   files abusive or false reports beyond the rate limit. Is that the right trade?
4. **CSAM reports and NCMEC.** A CSAM report only alerts staff. Whether and when a report (rather than a confirmed
   hash) obliges us to file a CyberTipline report ourselves is for counsel and the runbook.
5. **Terms wording** in §4.1 (new CSAM paragraph) should be reviewed with the rest of the Terms.

**CI on PR #2378** (run 31293476664 / 31293476575, head `28a3bbab4`): `ci / Lint & TypeScript
Check` **FAILURE**, `ci / Unit Tests` **FAILURE**, `ci / E2E (agent-session user stories)`
**FAILURE**, `Security Test Suite` **FAILURE**, `Static Security Analysis` **FAILURE**. All five
fail on the same line — `web#build … Failed to compile … Property 'changed' does not exist`.

### Which commit broke it, and why neither branch was wrong

| Commit | `conflict` variant in the union | `applyWorkspaceMembershipWrite` | unnarrowed `result.changed` reads | compiles |
|---|---|---|---|---|
| `94e12bd83` — the cross-workspace chat-bind fix | **3** | 0 | 0 | ✓ |
| `3c12c9e75` — membership moves to the tree | 0 | **1** | **3** | ✓ |

The xws fix widened `ApplyWorkspaceNodeWriteResult` with a `conflict` variant on one line of
development. The membership runtime added three consumers that read `.changed` after narrowing away
only `refused` and `stale` on another. **Each branch compiled alone.** The merge is the first commit
where both exist, and it is the merge that was never typechecked.

`.pu-reports/pu-merge-client.md` — the report for that merge — lists its gates as:

> `@pagespace/lib` typecheck 0 · `test -- src/agent-workspaces` 682 passed / 21 files · web
> `left-sidebar` 94 passed / 6 files · web `stores/agent-workspace` 90 passed / 4 files

**`web typecheck` is not in that list.** The branch report it superseded, `pu-fix-xws.md`, *did* run
it (`bun run --filter web typecheck` → exit 0) and recorded it in a gate table. The merge agent
narrowed the gate set relative to the branch it was merging, on the one commit where a *merge* was
the only thing that could have introduced the fault. The merge's own heading is "Verified, not
assumed."

### It is not only a type error — it is a live mistranslation of the refusal the fix added

`commitUnderLock` (`workspace-node-runtime.ts:273`) contains the database backstop that **returns**
`{ status: 'conflict', code: 'target_already_shown' }` when the `agent_workspace_nodes_chat_target_idx`
unique index rejects a bind. It returns rather than throws, so
`applyWorkspaceMembershipWrite`'s own `catch` — which translates a *thrown* chat-target conflict
into the handled `refused` / `bound_elsewhere` — never sees it. The `conflict` passes straight
through to the three callers:

- **`agent-workspaces-runtime.ts:306`** — `admitConversation`. Narrows `refused`, narrows `stale`,
  then `if (!result.changed) return 'already_a_member'`. On a `conflict`, `result.changed` is
  `undefined` → **the caller is told `'already_a_member'`**. A worker spawn, an HTTP claim, or the
  global auto-bind that was refused because the conversation is held by another workspace is
  reported as a benign no-op.
- **`:545`** — `dismissConversation` → a conflict reports `'already_parked'`.
- **`:577`** — `readmitConversation` → a conflict reports `'already_attached'`.

This is the exact race the backstop's own comment says it exists for: "the advisory lock is per
workspace, and the two callers racing for one conversation are in two of them by definition."

And it contradicts the changelog this epic shipped (`65670cd57`), which promises users:

> **Opening a conversation that is already open in another session says so**

At the membership layer it does not say so. It says "already a member."

### Why the tests were green

Coverage for `target_already_shown` exists — `workspace-node-runtime.test.ts:394`, `:498`,
`workspace-node-chat-binding.integration.test.ts:168`, `:272` — but **all of it sits at the
`workspace-node-runtime` layer**, above the three membership callers. There is no test at
`agent-workspaces-runtime` that drives a conflict through `admitConversation` /
`dismissConversation` / `readmitConversation`. A layer got a new outcome and its consumers got no
test, which is why 682 lib tests and four named conflict tests all pass over a build that does not
compile.

**Method note, and it matters.** My first pass ran `git grep <pattern> <sha> -- $FILES` and returned
zero for every pattern. That was wrong: several changed paths contain `[workspaceId]`, which
`git grep` treats as a glob pathspec, so the pathspec matched nothing and every scan silently
returned clean. The numbers above come from `grep` against the real checkout. The previous audit
reported the same all-zero table and described its method as `git grep`/`git show` against the ref —
**that result should be treated as unverified**, not because its conclusion was wrong (it holds
here) but because the technique cannot distinguish "clean" from "scanned nothing". Any future audit
of this repo should grep a checkout, or use `:(literal)` pathspecs.
